# CLAUDE.md — DawnOfTermina (fonte única da verdade)

Recompilação estática nativa de *Majora's Mask 3D* (3DS, ARM11) para C++20 + Vulkan. Leia este arquivo antes de qualquer alteração e atualize-o ao final de cada etapa.

## Regras inegociáveis

1. **Bring-your-own-ROM.** Nunca commitar `.cia`, `.ncch`, `.bin` (`code.bin`, `exheader.bin`), `romfs/`, `exefs/` ou qualquer asset da Nintendo. Dados extraídos vivem só em `game_data/` (ignorado). A cópia do usuário fica em `ISO/` (ignorado). Antes de cada commit: `git status` e conferir que nada disso está staged.
2. **Commits sem co-autoria de IA.** Nenhum `Co-Authored-By`, trailer ou assinatura de IA. Apenas a autoria do `git config` do usuário.
3. **Um commit por etapa/módulo**, somente após o build passar. Atualizar este arquivo (e a tabela de status do `README.md`) antes do commit.
4. **Licença GPL-3.0-or-later.** Todo arquivo-fonte original começa com o cabeçalho GPL (modelo em `src/main.cpp`).
5. **Fluxo de branches.** Nenhum commit de desenvolvimento direto na `main`. Todo trabalho ocorre na `dev` (ou em branches de feature derivadas dela), com commits limpos por etapa. Para integrar: `gh pr create --base main --head dev` e aguardar aprovação/merge. A `main` está protegida no GitHub (PR obrigatório, 0 aprovações exigidas, administrador isento: `enforce_admins` desligado).

## Convenções de código

- C++20, CMake ≥ 3.20, sem exceções em hot paths; tipos de largura fixa (`u8/u16/u32/s32` em `src/core/`).
- Módulos: `src/core/` (memória, tipos), `src/hle/` (serviços `nn::*`, `svc`), `src/gfx/vulkan/` (PICA200 → Vulkan), `src/game/` (código transcrito), `tools/` (Python/Shell).
- Toda função transcrita do jogo leva `// Original VA: 0xXXXXXXXX` e é nomeada igual ao símbolo renomeado no Hopper.
- `src/game/` organizado por subsistema (`scene/`, `actor/`, `audio/`, `collision/`, `ui/`...), um arquivo por unidade lógica.
- Comentários explicam o *porquê*; atalhos conhecidos usam `// shortcut: <limite>, <quando melhorar>`.

## Runtime (Etapa 3)

- **Espaço de endereçamento:** `core::Memory` reserva 4 GiB de host (`mmap PROT_NONE`) e mapeia regiões sob demanda; VA do guest → host = `mem.host(va)` (uma soma). Páginas não mapeadas dão SIGSEGV, o que expõe transcrições erradas. Acesso: `mem.read<T>(va)` / `mem.write<T>(va, v)`.
- **Loader:** `core::load_code` lê `exheader.bin` + `exefs/code.bin`, mapeia `.text`/`.rodata` como somente leitura, `.data`+`.bss` e a stack (topo em `0x10000000`).
- **Modelo HLE (revisado na Etapa 6):** originalmente no nível do SDK (`nn::*` como chamadas C++ diretas). Com o recompilador, o HLE passou para o nível syscall/IPC (ver "HLE do kernel"); as APIs `hle::fs/hid/dsp` viram backends.
- `hle::svc`: `ControlMemory` (COMMIT/FREE/PROTECT, heap normal em `0x08000000` e linear em `0x14000000` via bump allocator, limite de 128 MB), `ExitProcess`, `SleepThread`, `GetSystemTick` (268.111.856 Hz), `Break`, `OutputDebugString`.
- `hle::srv`: `GetServiceHandle` devolve handles fixos para serviços conhecidos.
- `hle::fs`: `OpenFile("rom:/...")`/`GetSize`/`Read`/`Close` direto de `game_data/romfs/` (rejeita `..`).
- `hle::hid`: SDL3. Circle pad no anel do `hid:USER` (entradas `{botões, pressionados, soltos, s16 x, s16 y}` em PAD+0x28, valor cru em PAD+0x20; ±156, bits `CPAD_*` a partir de 41). Teclado: K/J/I/U = A/B/X/Y, Q/E = L/R, 1/3 = ZL/ZR, Enter/Backspace = Start/Select, setas = D-pad, WASD = circle pad. Controle no layout posicional da Nintendo (leste = A). **Toque** = botão esquerdo do mouse sobre a tela inferior (`hid::window_to_touch`, mesmo layout 400×480 do `Context::present`); arrastar para fora mantém a caneta na última posição. No `hid:USER` o touch fica em shared+0xA8: cabeçalho do anel, entrada raw em +0x18, 8 entradas `{u16 x, u16 y, u32 valid}` em +0x20.
- `hle::dsp`: HLE do firmware de áudio (ver "Áudio (DSP)").
- **C-stick:** pelo `ir:USER` (Circle Pad Pro virtual, ver "Experiência de PC"); o jogo não usa `ir:rst`.
- **Faltam:** saves (além do que o `fs` já grava em `saves/`).

## Gráficos (Etapa 4)

- **`gfx::vulkan::Context`** (`src/gfx/vulkan/`): instância (via SDL3), seleção de GPU (prefere discreta), device, swapchain FIFO recriada ao redimensionar/minimizar, 1 frame em voo. Apresenta as telas superior (400×240) e inferior (320×240) empilhadas em uma tela virtual de 400×480, escaladas com aspecto preservado (upload por staging + `vkCmdBlitImage`, filtro nearest).
  - Formato de swapchain: **UNORM + `SRGB_NONLINEAR`** obrigatório; framebuffers do 3DS já vêm com gama, e um formato `*_SRGB` ou espaço linear aplicaria a gama duas vezes (bug já visto: a SDL expõe espaços extras via `VK_EXT_swapchain_colorspace`).
  - `DOT_VULKAN_VALIDATION=1` liga a `VK_LAYER_KHRONOS_validation` se estiver instalada (pacote `vulkan-validation-layers`).
- **`gfx::pica::decode_texture`** (`src/gfx/pica/texture.*`): os 14 formatos PICA200 (RGBA8 … ETC1A4) → RGBA8 linear. Tiles 8×8 em ordem Morton (x nos bits 0/2/4, y em 1/3/5); ETC1 = 4 blocos 4×4 em ordem Z por tile, cada bloco u64 LE; ETC1A4 = u64 de alfa (nibble em `(x*4+y)*4`) antes de cada bloco. A saída fica na ordem da memória (linha 0 = primeira na memória; em texturas PICA é a base da imagem, convenção GL); inverter ao amostrar. Validado com o ícone SMDH real (48×48 RGB565 em `icon.bin+0x24C0`).
- **`gfx::pica::CommandProcessor`** (`src/gfx/pica/command_processor.*`): parser de command lists (`[valor][cabeçalho: id 0-15, máscara de bytes 16-19, extras 20-30, consecutivo 31]`, padding de 8 bytes), banco de 0x300 registradores, uploads do vertex shader (código 0x2CB/0x2CC, swizzle 0x2D5/0x2D6, uniforms float f24/f32 0x2C0/0x2C1 com auto-incremento, int 0x2B1, bool 0x2B0), gatilhos de draw 0x22E/0x22F via `on_draw`.
- **Shaders (4b, parte 1):**
  - `gfx::pica::parse_shbin` (`shbin.*`): DVLB/DVLP/DVLE (código, operand descriptors, programas, tabela de saídas); `outmap_from_outputs` deriva os registradores VS_OUTMAP de um DVLE.
  - `gfx::pica::generate_vertex_shader` (`shader_gen.*`): PICA VS → GLSL 450. Só traduz o código **alcançável a partir do entry point** (blobs são compartilhados entre VS e GS). **Especializado** nos uniforms bool (`b0..b15`) e int (`i0..i3`) do draw e emitido como código **estruturado** (sem dispatcher `switch(pc)`, que fazia o Mesa levar minutos): IFU/CALLU/JMPU resolvidos estaticamente, CALL inlined, LOOP vira `for` com contagem conhecida (`i.x+1` iterações, `aL += i.z`; BREAK/BREAKC = `break`), IFC/CALLC viram `if`, JMPC vira `if/else` sobre o resto do frame (cauda duplicada; só saltos para frente dentro do frame — o GzwShader tem um `JMPU` que sai de uma região de JMPC). Fluxo não estruturável (salto para trás, BREAK fora de loop, orçamento de 32k instruções estourado) devolve erro e o renderer usa o interpretador na CPU. Multiplicação "sanitizada" (0·∞ = 0), MAX/MIN no estilo PICA, endereçamento relativo de uniforms com clamp. Saídas empacotadas nos varyings fixos pelo OUTMAP; `gl_Position.z = -z` (PICA usa [-w, 0]). Não suportado (erro explícito): EMIT/SETEMIT (geometry shader) e LITP.
  - `gfx::pica::generate_fragment_shader`: 6 estágios TEV (fontes, operandos, 10 operações, escala 1/2/4×, buffer de combinador com atualização por estágio, DOT3_RGBA), alpha test. Valores que mudam por draw (6 cores constantes do TEV, cor inicial do buffer, referência do alpha test) vão por **push constants** (`fragment_push_constants`, 32 bytes), não no texto do shader — antes geravam uma variante por cor.
  - `gfx::vulkan::compile_glsl` (`spirv.*`): GLSL → SPIR-V 1.3 com glslang (`find_package(glslang CONFIG)`).
  - Validação: os **6 programas de vértice reais** do jogo (`romfs/shaders/*.shbin`) geram SPIR-V aceito pelo `spirv-val --target-env vulkan1.1`; o único geometry shader (LineShader) é recusado com erro claro.
- **Draws (4b, parte 2):** `gfx/vulkan/renderer.*`. Vertex fetch (`gfx/pica/vertex_loader.*`: loaders, formatos, permutação, atributos fixos, índices — draws indexados mantêm o index buffer, ver "Custo por draw do renderer"; **offsets somados no espaço físico** — a base costuma ser o início da VRAM e os dados estão na FCRAM). **Vertex shader na GPU**: módulo gerado por (código + swizzles + entry + bools + ints + OUTMAP), em cache; os vértices crus (`VertexInput`, 16 `vec4`) vão como atributos 0–15. Se o programa não estrutura, **fallback na CPU** (`gfx/pica/shader_interp.*`, mesma semântica) com vértices empacotados pelo OUTMAP e um VS de repasse. Os 6 programas do jogo rodam todos na GPU. Fragment shader = TEV gerado (cache por hash), texturas das unidades 0–2 (cache por conteúdo), blend/depth/cull/scissor/viewport dos registradores, profundidade = `z/w·scale + offset` (0x4D/0x4E). Render targets: ver "Cache de superfícies" abaixo; depth só na GPU, limpo pelo último `MemoryFill` do endereço. **Convenção de linhas:** color buffers e texturas do PICA são de baixo para cima (linha de memória r = y de janela H−1−r). Command lists seguem **saltos de buffer** (`0x238`–`0x23D`). Framebuffers do GSP chegam como **endereços virtuais**.
- **Iluminação por fragmento:** ligada se `0x8F` bit 0 e não `0x1C6` bit 0. A *estrutura* (luzes ativas `0x1C2`/permutação `0x1D9`, config dos LUTs `0x1C3`/`0x1C4`, entradas/abs/escala `0x1D0`–`0x1D2`, config por luz, bump) é *baked* no fragment shader (`shader_gen.cpp::lighting`, modelo do Citra); cores, posições (f16), spot (s1.11) e atenuação (f20) são lidas em runtime de um SSBO (set 0 binding 1) com os registradores crus `0x140..0x1C0` + os 24 LUTs (`ShaderState::light_lut`, escritos via `0x1C5`/`0x1C8`+ no `CommandProcessor`). Resultado entra no TEV como fontes 1/2. **Formato da entrada de LUT:** valor 0.12 nos bits 0–11 e a diferença para a próxima entrada em **sinal-magnitude** (magnitude nos bits 12–22 ÷ 2047, sinal no bit 23; como o Citra). Lida como complemento de dois de 12 bits, `0x808` (−8) virava −2040: cada entrada caía de 1 a ~0 dentro de si mesma e toda luz pontual com atenuação por distância desenhava anéis concêntricos (chão sob o Link na queda do tronco, tochas da Clock Tower, cena Deku). Achado com o savestate antes da queda: `DOT_SKIP_TEX` (bisseção → chão `1F48CE80`), `DOT_DEBUG_FS=nolight` (some) e `nodist` (some), dump do LUT 16. Validado em 1× e em 3× com 16:9 pelos dumps do mesmo trecho. Validado: a máscara da abertura, o Happy Mask Salesman e a cutscene da Lost Woods (Link, Epona, Tatl/Tael, Skull Kid) aparecem iluminados. Sem shadow maps. **Spot:** índice `dot(light_vector, spot_dir)` (registradores guardam a direção *inversa*, convenção do Citra) — **não verificado com dados reais**: um trace dos registradores `0x140..0x1DF` da abertura até a Lost Woods não encontrou nenhuma luz com spot habilitado (`0x1C4` bits 8–15 sempre 1).
- **Cache de superfícies na GPU (Etapa 9)** — `renderer.cpp`: cada color buffer vira uma `Surface` residente na GPU, **indexada pelo VA**, em `DOT_RES_SCALE`× a resolução do guest (`1`–`8` ou `native` = maior inteiro que cabe na janela inicial; padrão 1). Depth buffers são imagens à parte indexadas pelo VA do depth (framebuffers por par cor/depth). Todas as imagens do cache ficam em layout `GENERAL` (attachment, amostragem, blit e clear sem rastrear layouts; só barreiras de memória). Viewport e scissor são multiplicados pela escala; filtragem anisotrópica (até 16×) nos samplers lineares quando a escala é > 1.
  - **Sem readback por quadro:** a memória do guest só é atualizada (`readback`: blit para o tamanho do guest + cópia + tiling na CPU) quando uma operação GX feita na CPU (DMA, TextureCopy, DisplayTransfer que a GPU não trata, `ImportDisplayCaptureInfo`) toca a superfície (`Renderer::sync`, chamado pelo `settle` do GSP), ou quando uma textura sobrepõe parte de uma superfície. Escritas da CPU são detectadas por **hash da memória** ao reusar a superfície (aí ela é recarregada da memória). Leituras diretas da CPU **não** são detectadas (sem falta de página em leitura): `DOT_READBACK=1` volta a fazer as transferências na CPU (readback por quadro). Na abertura e no título: **0 readbacks** (eram ~3 por quadro, 512×400) e ~25% mais quadros por segundo em 1×.
  - **Render-to-texture:** textura com o mesmo endereço, largura e formato de uma superfície amostra a superfície (em alta resolução). Se a textura for mais alta (padding de potência de 2, ex.: 256×256 sobre 256×200), amostra uma cópia acolchoada (blit para as últimas linhas da imagem = primeiras linhas de memória).
  - **Listras/anéis da queda do tronco, cena Deku e porta da Clock Tower: resolvido (Etapa 4, iluminação).** Não eram refração nem superfícies do cache: eram os **LUTs de iluminação** (ver "Iluminação por fragmento"). Hipóteses descartadas no caminho, todas medidas: crop de superfície alargada, mipmaps, textura projetada (nenhum draw usa tipo ≠ 2D), resolução da captura do blur de zoom (`1F300000`).
  - **`MemoryFill`** continua na memória e, se começar numa superfície e a cobrir inteira, vira `vkCmdClearColorImage` (cor decodificada da própria memória preenchida); limpa também o depth daquele endereço.
  - **`DisplayTransfer` na GPU:** origem = superfície que contém `in` com a mesma largura, possivelmente **a partir de uma linha de tile** (o jogo desenha as duas telas no mesmo buffer 512×400, uma depois da outra; a de baixo é transferida da linha 80). Tiled→tiled (cópias reduzidas usadas como textura) = blit com filtro linear para outra superfície. Tiled→linear (framebuffer) = compute shader (`TRANSFER_CS`) que já gira para a orientação da tela (linha do framebuffer = coluna da tela) com flip e downscale 2×1/2×2 (o topo é renderizado em 480×400 e reduzido em X); o resultado é uma `Display` por endereço de saída, apresentada direto pelo `Context::present` (blit linear). O GSP guarda essas transferências e, se a CPU precisar dos bytes do framebuffer, as refaz na CPU (`settle`).
  - `DOT_DUMP_FRAMES` grava as telas na resolução escalada (lidas da GPU).
- **Widescreen (Etapa 10)** — `DOT_WIDESCREEN=window` (recomendado) faz a tela de cima ter a proporção da janela; `<w>:<h>` (ex.: `16:9`, `21:9`) fixa a proporção (re-avaliada a cada bind; mudou → superfícies largas recriadas). Desligado por padrão. Mecanismo (sem procurar matrizes nos uniforms, que variam por shader e vêm com a rotação de 90° do 3DS embutida):
  - A tela de cima é renderizada girada: as **linhas** do color buffer são o eixo horizontal da tela. A superfície que alimenta um `DisplayTransfer` de 400 linhas (a tela de cima) entra em `wide_vas` e passa a ter `image_h = altura × escala × W` (W = proporção / (5/3)); viewport e scissor em Y usam `Surface::sy()`. Upload/readback/blits/compute usam `image_h`, então o resto do pipeline continua igual.
  - Por draw (`widescreen_clip`), só nos que cobrem a tela inteira (viewport em Y = 0..altura): o clip-y é multiplicado por 1/W (`u.depth.z` no UBO, aplicado no vertex shader gerado e no de repasse). Perspectiva (w ≠ 1 nos 3 primeiros vértices, calculados pelo interpretador na CPU) → mais campo de visão lateral sem distorção. Ortográfico → HUD, textos e caixas de diálogo **centralizados na proporção original**; exceção: quads ortográficos que vão de borda a borda (clip y de −1 a 1, até 64 vértices: fades, composições de bloom) continuam esticados até as bordas.
  - Draws da tela de baixo (viewport de 320 linhas no mesmo buffer) só ficam esticados na imagem e são reamostrados de volta a 320 colunas no compute da transferência (`b.x`), sem distorção. Cópias tiled→tiled de uma superfície larga (bloom) levam a imagem inteira comprimida; o quad de tela cheia que as usa a estica de volta.
  - **Layout** (`src/gfx/layout.h`, usado pelo `Context::present` e pelo toque do mouse em `hid::window_to_touch`): modo **tela única** (`gfx::g_single_screen`, padrão) = a tela de cima (de qualquer largura) **preenche a janela** e a de baixo é uma sobreposição no canto inferior direito (30% da altura; **Tab** mostra/esconde); modo **duas telas** = empilhadas, a de baixo centrada sob a de cima; modo **N64** (padrão, ver "Tela única N64"). `DOT_WINDOW=<w>x<h>` define o tamanho inicial da janela; **F11** alterna tela cheia. Com widescreen, `DOT_RES_SCALE=native` = altura da janela / 240 (720p → 3×, 1080p → 4×).
  - Validação: dumps do renderer (`DOT_DUMP_FRAMES`, imagem da tela de cima já alargada) + layout coberto pelo self-test do toque. **Não usar capturas de tela do desktop** (`spectacle`/`import`): pegam outras janelas do usuário.
  - **Limites:** o jogo faz culling pelo FOV original, então objetos podem aparecer/sumir nas laterais; HUD não é ancorado nas bordas (fica no centro 5:3).
- **60 FPS por interpolação (Etapa 11)** — `DOT_FPS=60` (ou `90`/`120`: 2/3 intermediários por quadro; `fps` no `config.toml` e no F1).
  - **Frame pacing do jogo (RE no Hopper):** `MainLoop_Frame` (`0x10677C`) termina em `GfxManager_SwapAndWait` (`0x124EE8`), que chama `nngxWaitVSync` (`0x13765C`) até o contador de VSync (`0x6A3A08`) alcançar o alvo em `GfxManager+0xD0`. O gerenciador é `*(0x6A3A4C)` (`GetGfxManager`, `0x1D71AC`). O alvo é escrito em `0x108F94` como `vcount + *(0x6A3A14)`: **`0x6A3A14` é o `frame_step` (2 = 30 FPS)**. `+0xCC` acumula o atraso em VBlanks, limitado a `+0xC8` (16). O único modo de 60 FPS do jogo é a cena de créditos: `EndingScene_Init` (`0x15D20C`) põe step 1 e limite 8, e `EndingScene_Destroy` (`0x170680`) volta a 2/16. `0x126D78` usa `2/step` como escala, mas só nessa cena.
  - **Por que não destravar o step:** a lógica é de passo fixo por quadro. Forçar `0x6A3A14 = 1` (testado) faz a abertura correr **2× mais rápido**: animações, cutscenes e o relógio dos 3 dias avançariam por quadro.
  - **Interpolação no renderer:** a simulação continua a 30 Hz (timers e física intactos por construção). O renderer grava as operações de GPU do quadro (draws com registradores + `ShaderState` deduplicado, fills, transfers). Na transferência que fecha o quadro da tela de cima (saída linear de 400 linhas), reexecuta o quadro com os **uniforms float do vertex shader** (matrizes de câmera, modelo e ossos) **interpolados com o draw correspondente do quadro anterior** (fração k/N, N = `DOT_FPS`/30, uma reexecução por intermediário). A chave é programa + buffers de atributo + índices/contagem + textura 0 + color buffer (**sem ordinal**): instâncias da mesma malha/atlas (NPCs, painéis do HUD) dividem a chave e cada draw pega o draw não usado do quadro anterior com os **uniforms mais próximos** (grupos > 32 = por ordem, limite de custo). Draw casado com mudança relativa > 0,05 é desenhado como no quadro real (sem média). Antes, por ordinal: em Clock Town um prompt "View" e os anéis dos botões apareciam só nos quadros intermediários (painel mediado com um irmão); medido com `DOT_DUMP_INTERP` + diff contra os dois reais: 3 quadros com artefato em 240 → 0, pixels fora do intervalo entre os reais 2,9% → 1,2% no pior quadro. O resultado vai para imagens extras (`Display::interp[k]`).
  - **Ritmo de apresentação (linha do tempo, modelo de amostras do TriAevum):** cada imagem da tela de cima (real ou intermediária) vira um `Shot` com **tempo de conteúdo em VBlanks do guest** (real = contagem de VBlanks na transferência, `Renderer::vblank` chamado pelo GSP; intermediárias igualmente espaçadas desde o real anterior). O apresentador mostra o shot mais novo com tempo ≤ um **relógio de exibição** que anda a latência fixa atrás do relógio de VBlank: `intervalo·(1−1/N) + atraso medido + 0,1` (atraso = quanto depois do tempo de conteúdo o último shot ficou pronto, máximo recente com decaimento). O relógio avança pelo passo médio do monitor e é puxado 5% por apresentação para o alvo (jitter do momento da apresentação não troca imagem na fronteira; erro > 2 VBlanks = ressincroniza). `display()` da tela de cima **não pega o `lock` do renderer** (só `shots_lock`): a thread do jogo segura o `lock` durante as reexecuções e o apresentador perdia o VSync esperando; as outras telas usam `try_lock` e a última imagem. **Antes:** o intermediário ficava "metade do intervalo depois de pronto", mas a tela só passa para o framebuffer novo no próximo swap de VBlank do GSP, e a janela muitas vezes já tinha passado → medido (abertura → Lost Woods, 720p/60): **25% das apresentações avançavam uma imagem**, o resto repetia ou pulava. **Agora: 96–98%** (o resto: cortes, troca de cena, deriva 59,83 × 60 Hz ≈ 1 repetição a cada 6 s). `DOT_STATS` mostra `presents smooth/repeated/skipped`.
  - **Translações de UV (piscadas de textura):** o jogo "dá a volta" na rolagem de texturas (ex.: `-0,9958 → 0`) e troca células de flipbook (`c94.y` 0 → ¼ → ½ → ¾); a média linear punha a textura meio período fora ou misturava células = piscada no intermediário. Modelo do TriAevum (`PicaTextureTranslation`): translação pós-linear de escala ±1 + período do wrap (Repeat 1, Mirrored 2) → caminho mais curto. Eles reconhecem o shader do OoT3D por hash; aqui a prova é **por draw** (`uv_fixes`): componente que mudou ≥ 1/16 e |valor| ≤ 8 → roda o VS na CPU em 2 vértices com +1,0 nele; só vale se exatamente uma saída de coordenada de textura (semânticas 12–15, 22–23) muda ±1 e nada mais muda (resultado em cache por draw+componente). Período = de todas as unidades habilitadas que leem aquela coordenada (unidade 2 pode ler a 1, bit 13 de `0x080`); proctex ligado → recusa. Salto > 1/8 (inclusive em atlas com clamp) = troca de célula: valor antigo antes de t = ½, novo depois. Achado no roteiro: **o GzwShader tem o mesmo layout do shader do OoT3D** (translações em `c10–c18.w`). Medido em 180 s: 22 voltas + 41 trocas de célula corrigidas. `DOT_STATS` → `uv wrapped/stepped`.
  - **720p a 60 FPS (Iris Xe), confirmado com tudo isso:** 30 quadros reais/s e 60 VBlanks/s nos 360 s do roteiro (abertura → Lost Woods), 96% das apresentações suaves.
  - **90/120 FPS:** só fazem sentido com monitor de taxa alta (ou sem VSync). Custo na thread do jogo: na Iris Xe a 720p, 120 FPS (3 reexecuções) derruba o jogo de 30 para ~20 quadros reais/s nas cenas 3D da Lost Woods; 60 FPS mantém 30.
  - **Câmera rígida (porte do DekUI, `src/gfx/camera_midpoint.h`):** no GzwShader (shader do mundo) c0–c3 = projeção (última linha `0 0 −1 0`), c20+3b = paleta de ossos em espaço de vista (10 ossos × 3 linhas), c70–c72 = câmera→mundo (translação = olho). Draw casado com essas duas assinaturas nos dois quadros (rigidez com tolerância do DekUI) → câmera intermediária = ponto médio por quaternion + média das translações; cada osso vai para o mundo (`C·MV`), é mediado lá e volta pela vista intermediária. Antes, a média linear das matrizes de vista encolhia a cena em giros rápidos. Os outros uniforms continuam na média linear. **Corte** também quando a maioria desses draws tem a câmera andando > 250 unidades ou girando > 45° (teste do DekUI), além do detector por variação relativa. Medido (roteiro até ~330 s, 60 FPS): ~78% dos draws pelo caminho da câmera, 99% dos quadros interpolados; `DOT_STATS` mostra `camera draws`.
  - **Reexecução fora da thread do jogo (câmera lenta em Clock Town, corrigido):** com 60 FPS em South Clock Town o jogo caía de 30 para **~20 quadros reais/s** (câmera lenta), igual com ou sem VSync. Linha do tempo no GSP: a thread que envia as listas usa ~10,6 ms de CPU por quadro; a lógica roda em **outra thread do guest**, e as threads do guest se revezam (baton). A reexecução (~6–7 ms, ~100 draws) rodava dentro do `DisplayTransfer` segurando o baton, então o quadro passava do 2º VBlank e o jogo esperava o 3º (3 VBlanks/quadro = 20 FPS). Agora o `end_frame` só marca o quadro como pendente (`job`) e uma thread do renderer (`worker`) faz a reexecução sob o `lock`, em paralelo com a lógica do jogo; toda entrada pública do renderer usa `acquire()`, que roda uma reexecução ainda não iniciada antes (a ordem do trabalho de GPU não muda). Para rodar ao lado do guest, a reexecução **não lê a memória do guest**: o `Op` guarda os vértices já carregados no quadro real e o fator de clip do widescreen, o `MemoryFill` guarda a cor; durante a reexecução não há hash/upload de superfície, hash de textura (usa a do quadro real) nem `sync`. Medido (save em South Clock Town, 720p 3×, 16:9): 60 FPS **29,2–29,9 quadros reais/s** (eram ~20), 60 VBlanks/s, 99% das apresentações suaves, sem underrun de áudio; 30 FPS inalterado.
  - Reexecutar só funciona porque, no fim do quadro, a memória do guest ainda tem tudo o que o quadro usou (no 3DS a GPU lê depois, então o jogo não pode ter reaproveitado). Só a tela de cima é interpolada. Se menos da metade dos draws casar (troca de cena), o quadro real aparece duas vezes. **Corte de câmera:** os mesmos objetos aparecem nos dois quadros, então quase tudo casa e a média das câmeras punha personagens onde nenhum dos dois quadros os tem (glitch visto na abertura). Detector: mudança relativa dos uniforms (Σ|a−b| / Σ(|a|+|b|)) por draw casado; mediana **dos draws do mundo** (câmera rígida; todos se não houver) > 0,025 = corte (com o HD HUD a maioria dos draws é 2D estática e segurava a mediana baixa nos cortes) → quadro real duas vezes. Medido: quadros normais ~0,0001 (p90 0,0013, giros rápidos < 0,02), cortes 0,05–0,93. CPU-shading e vértices escritos pela CPU não são interpolados (só uniforms).
  - **Engasgos corrigidos:** a reexecução segura a thread do jogo dentro do handler do GSP esperando a GPU; nenhum periódico rodava nesse tempo e o kernel **descartava** os períodos perdidos → 42–50 VBlanks/s (jogo lento) e áudio sem quadros. Agora o kernel repõe os períodos atrasados até 150 ms (`run_due_periodic`, `MAX_LAG`; cada VBlank enfileira sua interrupção no GSP) → 60 VBlanks/s nos dois modos.
  - **720p a 60 FPS na Iris Xe:** o que derrubava o jogo para 15–20 quadros reais/s **não era a GPU** (timestamps: ~30% ocupada em 3× com interpolação) e sim esperas da thread do jogo: (1) toda submissão esperava a GPU; (2) o buffer de vértices de 8 MB (vértices de 256 bytes) enchia ~10×/quadro, cada vez uma submissão; (3) um depth buffer era destruído/recriado ~100×/s (ver Submissão em lote). Corrigido isso: **30 quadros reais/s e 60 VBlanks/s em 500 s de roteiro (abertura → Link controlável), apresentação a 60 Hz, 99% dos quadros interpolados**, CPU do guest ~30%. O `config.toml` novo continua com 30 FPS (60 depende da GPU de cada um).
  - **Custo:** a reexecução roda na thread do jogo. Para caber nela, o fragment shader é memoizado pelos registradores que o gerador lê (`fragment_shader`; `DOT_VERIFY_FS=1` confere contra a geração completa), as texturas usam um hash por palavras e as superfícies um hash amostrado. Resultado: 594 quadros do jogo contra 615 sem interpolação no mesmo trecho (antes das otimizações caía para 416). `DOT_STATS` mostra `interpolated n/m`; `DOT_DUMP_INTERP=1` grava também os quadros intermediários (`interp_N.ppm`).
- **Submissão em lote:** os draws são gravados num único command buffer aberto; vértices (64 MB), uniforms, iluminação (deduplicada) e staging são sub-alocados linearmente por lote (offsets alinhados a 256). **Pipeline CPU/GPU:** há 3 conjuntos de recursos por lote (`Slot`: command buffer, fence, pool de descritores, buffers); `submit()` envia sem esperar e passa para o próximo conjunto (esperando só a fence do uso anterior dele), no fim de quadro (`DisplayTransfer` para framebuffer) e quando um buffer/o pool (1024 draws) enche. `submit_and_wait()` (espera tudo) só onde a CPU lê da GPU (readback, dumps) ou destrói recursos. A ordem não precisa de espera: uma fila só, e os lotes e o apresentador começam com barreiras completas, que cobrem tudo o que foi submetido antes. **Depth:** um por (endereço, tamanho) — dois color buffers de tamanhos diferentes usam o mesmo endereço de depth no quadro, e a imagem única era recriada com espera total ~100×/s; o `MemoryFill` limpa todos os depths do endereço. Comandos gravados executam em ordem atrás de barreiras completas, então reenviar uma textura no meio do lote é seguro.
- **Fog (modo 5 de `0xE0`):** cor `0xE1` (push constant), LUT de 128 entradas (`0xE6` índice, `0xE8`–`0xEF` dados; `{bits 0-12 diferença s1.11, 13-23 valor 0.11}`) em `ShaderState::fog_lut`, enviada no fim do SSBO da iluminação. Índice = `gl_FragCoord.z` (já é a profundidade de janela do PICA, mesma convenção do Citra), invertido se `0xE0` bit 16. A Lost Woods usa fog (neblina azul ao fundo). Gas (modo 7) não implementado.
- **Stencil:** depth buffer `D32_SFLOAT_S8_UINT` (fallback D24S8). Teste/ops (`0x105` enable/func, `0x106` fail/zfail/zpass) no pipeline; referência, máscara de comparação e de escrita como estado dinâmico. Só com depth D24S8 (`0x116` = 3). `0x115`: bit 0 = escrita de stencil, bit 1 = escrita de depth (confirmado no trace: o jogo usa 2). `MemoryFill` de 32 bits limpa o stencil com o byte alto. **Não validado com dados reais:** da abertura ao Skull Kid nenhum draw liga o stencil.
- **Falta (4b):** gas, shadow maps, logic op, geometry shader, depth de volta à memória, MSAA, escala que acompanha o redimensionamento da janela, despejo de superfícies antigas do cache.
- **Diagnóstico gráfico:** `DOT_DUMP_TEX=<dir>` (cada textura decodificada uma vez, cor | alfa, nome `VA_WxH_fFMT_pPARAM`), `DOT_SKIP_TEX=<va,...>` (pula os draws que amostram essas texturas: bisseção com um savestate), `DOT_TRACE_TEXVA=<va>` (estado completo dos draws que usam a textura: unidades, TEV, fog, LOD, faixa de cada saída do VS), `DOT_TRACE_LIGHT=1` (luzes por conjunto distinto de registradores), `DOT_DEBUG_FS=nolight|nofog|nospot|nodist` (tira um termo do fragment shader; `nolight` põe cinza), `DOT_TRACE_TEX=1` (texturas que casam com superfícies + estado do draw), `DOT_DUMP_FRAMES=<dir>` (telas em PPM), `DOT_DUMP_TARGETS=<dir>` (render targets a cada readback), `DOT_TRACE_FB=1` (fills/transfers/command lists/draws, superfícies novas, readbacks e o motivo), `DOT_TRACE_DRAWS=1`, `DOT_TRACE_SHADERS=1`.
- **Falta (antigo):** GSP HLE (`gsp::Gpu`: framebuffers, `DisplayTransfer`, `MemoryFill`, submissão de command lists, conversão PA↔VA: VRAM PA `0x18000000`↔VA `0x1F000000`, FCRAM PA `0x20000000`↔heap linear VA `0x14000000`); leitura de vertex arrays/índices (formatos de atributo, loaders 0x200+); upload dos uniforms (f24/f32/int/bool) para o UBO; amostragem por texture unit (0x80+: endereço, tamanho, formato, wrap/filtro) com cache de texturas decodificadas; iluminação por fragmento, fog, proctex; geometry shader; estado de blend/depth/stencil/cull; render passes/pipelines com cache; render targets na VRAM; geometry shader e atributos fixos (0x232).

## Áudio (DSP) — `src/hle/dsp.*` + `src/hle/service/dsp.cpp`

- **Protocolo** (RE no Hopper de `nn_snd_InitializeDspShared` `0x1631c8`): `WriteProcessPipe(2, Initialize)` → o app lê do pipe 2 a contagem (15) e os 15 endereços DSP (palavras de 16 bits) e converte **cada um duas vezes** com `ConvertProcessAddressFromDspDram`: `addr` e `addr | 0x10000` → **duas regiões**, VA `0x1FF50000` e `0x1FF70000` (DSP word `w` → VA `0x1FF40000 + 2w`). O app escreve 4 no contador da região 0 e depois alterna: a região com **contador maior** (com wrap) é a que ele acabou de preencher; o DSP lê a config dela e escreve os status na outra (protocolo do Citra). O DSP **não** escreve o contador. Strides confirmados no Hopper: config de voz `0xC0`, status `0x0C`, coeficientes ADPCM `0x20`; a ordem das 15 estruturas é a do Citra (contador, configs, status, coeficientes, config do DSP, status do DSP, final samples, intermediate mix (2 × 0xA00), compressor, debug, 5 desconhecidas). O empacotamento dentro da região é nosso (`STRUCT_OFFSET` em `dsp.h`; cabe em 0x10000 bytes).
- **Config de voz** (offsets em `hle::dsp::cfg`, validados com dados reais: rate 0,674 = 22050/32728 Hz, stream estéreo da música em duas vozes com ganho 0,5/0 e 0/0,5 e rate 0,978 = 32000 Hz, fade de ganho ao apertar START): `dirty` u32 @0 (bits do Citra: 16 enable, 18 rate, 19 fila, 25 ganho 0, 28 sync, 29 reset, 30 buffer embutido…), ganho `float[3][4]` @4, rate @0x34, fila de 4 buffers (`0x14` bytes) @0x4C com bitmap @0x4A, enable @0xA0, sync @0xA2, play position @0xA4, buffer embutido (endereço físico @0xAC, tamanho em samples @0xB0, formato/mono-estéreo @0xB4, `yn` @0xB8, loop @0xBC, id @0xBE). Campos `u32` do DSP guardam a **metade alta primeiro**. Status: enabled @0, id dirty @1, sync @2, posição @4, id atual @8, anterior @0xA. Config do DSP: dirty @0, master volume @4 (bit 17).
- **Mixer** (`process_frame`, chamado a cada 160 samples de 32.728 Hz pelo periódico do serviço): fila ordenada por id (menor primeiro), buffer embutido, loop (o buffer volta à fila), decodificação PCM8/PCM16/DSP-ADPCM (`decode_adpcm`, quadros de 8 bytes, `yn1/yn2`, 8 pares de coeficientes por voz) do buffer inteiro ao desenfileirar, interpolação linear, mix 0 com quad → estéreo (frente + trás), master volume. Voz que esvazia a fila depois de tocar desliga (`enabled = 0`, id 0, id dirty), como no Citra. Flags dirty são zeradas na memória após o parse.
- **Relógio de áudio:** periódico do kernel (160/32728 s = 4.888.780 ns), com os períodos atrasados repostos (até 150 ms). **Não usar uma thread de tempo real separada** (tentado): o DSP seguia mixando enquanto a thread do jogo estava presa numa chamada HLE longa, a thread de som do jogo não reabastecia as vozes, elas esvaziavam e desligavam (**música parando**), e o thread 8 do guest chegou a entrar em loop (jogo travado ~90 s após o boot). O picotado original vinha de chamadas HLE longas (esperas da GPU) + períodos descartados; resolvido pelo pipeline CPU/GPU do renderer e pela reposição de períodos.
- **Saída:** `SDL_OpenAudioDeviceStream` S16 estéreo 32.728 Hz (o SDL reamostra). No início e após um underrun, 30 ms de silêncio entram na frente (o dispositivo puxa blocos maiores que um quadro de 4,9 ms). Mais de 125 ms enfileirados → o quadro é descartado (evita latência crescente com `DOT_SPEED` > 1). Medido (720p/60, 160 s): 0 underruns, fila mínima ≈55 ms. Sem dispositivo, segue mudo.
- **Bug corrigido:** o handler `0x0C` (ConvertProcessAddressFromDspDram) lia o argumento depois do `reply()` sobrescrevê-lo, então todas as estruturas apontavam para `0x1FF40000` e o app nunca via o próprio contador.
- **Faltam (shortcut):** buses aux 1/2 (reverb/delay), filtros simple/biquad, interpolação polifásica, compressor, `final_samples`/`intermediate_mix` de volta para o app.
- **Diagnóstico:** `DOT_TRACE_AUDIO=1` imprime cada buffer novo (voz, formato, canais, endereço, tamanho, rate, ganho, loop).

## Recompilador estático (Etapa 6) — `tools/recomp/`

Decisão do usuário (2026-11-14): **tradutor automático ARM11 → C++** para o binário inteiro; transcrição manual fica para subsistemas que valham uma versão limpa.

- **Saída gerada só no build** (`build/recomp_gen/`, 64 chunks + `recomp_table.cpp` + `stats.txt`). É derivada do jogo: **nunca commitar**. O CMake roda o recompilador se `game_data/exefs/code.bin` existir (`DOT_GAME_DATA`) e compila `dot_game` com `-O1 -w -ffp-contract=off -fno-strict-aliasing` (~2 min com `-j6`).
- **ISA:** ARMv6K = ARM + **Thumb-1** (sem Thumb-2) + VFPv2. Lifters: `arm.py`, `thumb.py`, `vfp.py`; registro comum `common.py` (`Insn`: kind normal/branch/call/icall/ret/jump/trap).
- **Descoberta de funções** (`recomp.py`): descida recursiva do entry + `.init_array` (offsets relativos; limites lidos do loop do crt0, ver abaixo) + alvos de BL/BLX + literais de código, depois candidatos *vetados* (não podem cair em código já decodificado e precisam passar `plausible_walk`): ponteiros em `.rodata/.data`, `ADR` (`add/sub rd, pc, #imm`, ex. veneers ARM→Thumb) e `ldr rX,=off; add rX, pc` (PIC). ~16.150 funções, ~1,16 M instruções; ~55 traps estáticos, todos dados alcançados após chamadas noreturn.
- **Modelo de execução:** `u32 func_XXXXXXXX(recomp::Context*)` (chave = endereço | 1 se Thumb) **retorna o endereço para onde "voltou"**; o chamador compara com seu LR e, se diferir, despacha localmente (helpers de switch que mexem no LR). Saltos computados vão para um `switch` local de labels (alvos de `addls/ldrlo pc` do ARMCC limitados por `cmp`; `add pc, pc, rX, lsl #2` com outra condição = tabela de `b` ou, sem `b`, **laço desenrolado**: toda instrução seguinte até o primeiro desvio vira label — é o `__udivsi3`/`__divsi3` da libgcc no código GCC do Restoration, `addne pc` em `0x7D6E28`/`0x7E472C`; sem isso toda divisão do mod virava `Trap`, e o jogo "travava" ao sair da Clock Tower para South Clock Town, onde o `FixTime` do mod divide); todo alvo de tabela vira label, inclusive a instrução logo após o `ldrlo pc` (caso 0 em `0x4FDACC`, cena 0x4F; 22 tabelas assim no binário: sem o label o `switch` não achava o caso e saía para a tabela global como "entrada não descoberta"); se o alvo for o LR de entrada da função é um **retorno** (`pop {r3}; bx r3`); senão `recomp::call` pela tabela (`set_function_table`). Branch para outra entrada = tail call. `mov lr, pc; bx rX` = chamada.
- **Runtime** `src/recomp/runtime.{h,cpp}`: contexto (r0-r15, NZCVQ, GE, s0-s31, FPSCR, TLS, monitor exclusivo), acesso à memória do guest por `g_base + va`, flags, barrel shifter, SIMD/saturação ARMv6, VFP. STREX sempre sucede (uma thread por vez).
- **Fluxo de trabalho (fronteira):** rodar `./build/dawnoftermina game_data`; a execução para com `recomp::Trap` ou `hle::kernel::Unimplemented` dizendo o que falta (syscall, comando IPC de serviço, entrada indireta desconhecida). Entradas reais não descobertas → `tools/recomp/extra_entries.txt` (ou melhorar a descoberta, preferível). Depurar travas com `gdb` (backtrace mostra `func_<VA>`). Uma falha do guest para todas as threads; além do `guest: stopped:` no terminal, o título da janela muda e uma caixa de diálogo mostra o erro (antes parecia só um quadro congelado).
- **Testes:** `tools/recomp/test_lifter.py` (idiomas críticos de decodificação) e `tests/recomp_test.cpp` (flags, shifter, SIMD, VFP), ambos no `ctest`.
- **Estado do boot recompilado:** passa por todo o crt0/SDK init (locale, `srv:` por IPC, heap/device memory, objeto da MainThread, stdio com callbacks Thumb) e **para em `svcCreateThread` (0x08)** — entry `0x0012A15C`, prioridade 0x18, chamado de LR `0x0016236C`.

## Hooks nativos (Etapa 12)

- `tools/recomp/hooks.txt` (`<VA> <nome>`) → o recompilador emite `func_<VA>` como `return recomp::hooks::<nome>(c);` (declarados em `src/recomp/hooks.h`, implementados em `hooks.cpp`). Chamadas diretas, tail calls e a tabela indireta passam pelo hook. VA que não é entrada descoberta = erro no build. O hook só reproduz o contrato AAPCS (r0/s0 de resultado, memória escrita, retorna o LR de entrada).
- **Por `code.bin`:** o `hooks.txt` tem uma seção por `code.bin`: `[<versão> <SHA-256 do code.bin>]` — v1.1, `1.1+restoration-1.5.9` e `1.1+restoration-1.5.9-hd-hud` (o Restoration aplicado sobre a v1.1 volta ao layout da v1.0). **A seção da v1.0 pura foi removida** (só v1.1). O `recomp.py` calcula o hash do `code.bin` extraído e usa a seção que casa (`select_hooks`, testado em `tools/test_versions.py`); outro mod sobre a v1.1 compila **sem hooks**, com aviso (eles só aceleram). Endereços da v1.1: cada rotina da v1.0 achada num único lugar do `code.bin` v1.1 pelas instruções (offsets de `b`/`bl` ignorados; os alvos batem com as vizinhas: `memmove4`→`memcpy4`, `memset`→`memclr`→`memclr4`). Deslocamentos: libc em `0x30xxxx` +0x148, `memcpy4`/`sinf`/`cosf`/`atan2f` −0x10, `memclr` −0x34, `memset` +0x100, `memmove4` −0x24.
- **`.init_array` por versão:** `init_array_bounds` lê os limites do próprio loop do crt0 (`0x1009E0`, Thumb, igual nas duas versões: `ldr r4,[pc]; add r4,pc; ldr r5,[pc]; add r5,pc`) em vez de constantes. v1.0 `0x64A390..0x64A5D0`, v1.1 `0x64BB40..0x64BD80`, 144 construtores nas duas. Com as constantes da v1.0, a v1.1 parava no boot (chamada indireta para `0x0061ABA8`, construtor não descoberto).
- Endereços no layout da v1.0 (= Restoration; RVCT, achados no Hopper; nomes no `symbols.csv`): `__aeabi_memcpy` `0x300154`, `memcpy_src_dst` `0x300144` (r0/r1 trocados), `__aeabi_memcpy4` `0x1F28E8`, `__aeabi_memmove4` `0x14C364`, `__aeabi_memset` `0x137ED4` (dst, n, c), `__aeabi_memclr` `0x16E63C`, `__aeabi_memclr4` `0x300338`, `strlen` `0x3028E0`, `strcmp` `0x302E3C`, `sinf` `0x22A3AC`, `cosf` `0x22A234`, `atan2f` `0x1E4F78` (hard-float: s0/s1 → s0). `sqrtf` não existe como função (511 `vsqrt` inline). Leitura de arquivo não foi hookada: o `fs` já é HLE por IPC e não aparece no perfil.
- **Medição** (abertura → cutscene da Lost Woods, 150 s, roteiro padrão, CPU das threads `guest` ÷ VBlanks): sem hooks 2,42 / 2,51 / 2,56 ms por VBlank; com hooks 2,54 / 2,56. **Diferença dentro do ruído.** Perfil por amostragem (gdb, 201 amostras com a thread do jogo ativa): memcpy ≈1%; **~23% é o handler HLE do `TriggerCmdReqQueue` do GSP** (`gsp_command`: processamento das command lists/renderer na thread do jogo, chamado de `0x16506C`), ~5% `recomp::call` (era busca binária na tabela de 17 mil entradas; agora **O(1)**: `set_function_table` monta um índice direto `(chave − menor chave) / 2` → posição na tabela, ~11 MB de `u32`, e a chave exata é conferida para recusar entrada ARM chamada como Thumb e vice-versa). O GSP é o alvo que sobra para reduzir CPU de verdade.
- **Hooks de instrução** (`<VA> <nome> insn` no `hooks.txt`; equivalente às trocas de instrução por SVC do DekUI no dynarmic): o recompilador emite `recomp::hooks::<nome>(c);` **no lugar** daquela instrução ARM (condição mantida; tem de ser uma instrução de dados já decodificada, senão erro no build). O hook faz o trabalho da instrução trocada. Único uso: **FOV** (`fov_projection` em `0x18D570`/`0x18D584`, `vldr s0, [r4, #0x18]` ao montar a projeção a partir do FOV vertical; `[camera] fov`/`cutscene_fov` no `config.toml` e no F1, 45 = original, até 70; cutscene = câmera de topo viva em `*(0x656B5C)` com setting 9/10 no array de câmeras do Play via `*(0x72F5C0)+0x16C`). Endereços do layout v1.0 (= Restoration); na v1.1 sem mod ainda não mapeados (seção sem `insn`). Ponteiros só são seguidos se o `QueryMemory` diz que estão mapeados. Validado: FOV 65 na Lost Woods visivelmente mais aberto.
- Os hooks de cópia (`__aeabi_memcpy`, `memcpy_src_dst`, `memcpy4`, `memmove4`) usam `std::memmove`: sem UB em regiões sobrepostas.
- Threads do guest se chamam `guest` (`pthread_setname_np`): somar `utime+stime` de `/proc/<pid>/task/*` com esse nome dá a CPU do jogo; o perfil por gdb filtra por esse nome.

## HLE do kernel (nível syscall/IPC)

Com o binário todo recompilado, o próprio SDK roda e fala com os serviços por `svcSendSyncRequest` (command buffer em TLS+0x80). **A fronteira do HLE agora é o kernel**, como num emulador; as APIs C++ de `src/hle/{fs,hid,dsp}` passam a ser backends dos handlers IPC.
- `src/recomp/svc.cpp`: ABI de registradores das syscalls → `hle::svc` / `hle::kernel`. Implementadas: 0x01 ControlMemory, 0x02 QueryMemory, 0x03 ExitProcess, 0x0A SleepThread, 0x0B/0x0C prioridade, 0x13-0x19 mutex/semáforo/evento, 0x21/0x22 address arbiter, 0x23 CloseHandle, 0x24/0x25 WaitSynchronization(N), 0x27 DuplicateHandle (inclui pseudo-handles 0xFFFF8000/8001), 0x28 GetSystemTick, 0x2A/0x2B GetSystem/ProcessInfo, 0x2D ConnectToPort, 0x32 SendSyncRequest, 0x35/0x37 ids, 0x38-0x3A resource limits, 0x3C Break, 0x3D OutputDebugString; 0x33 OpenProcess (só o próprio pid) e 0x70 ControlProcessMemory (só PROTECT, no-op) para o boot do Project Restoration.
- `src/hle/kernel.{h,cpp}`: tabela de handles e objetos; esperas com uma thread só retornam timeout ou acusam deadlock (`Unimplemented`). Mapa de regiões para QueryMemory em `hle::svc::AddRegion`.
- Serviços IPC: `srv:` (RegisterClient, EnableNotification, GetServiceHandle — entrega sessão para **qualquer** nome; o primeiro comando a um serviço sem HLE vira trap com nome + cabeçalho).
- **Handles copiados em respostas IPC:** `send_sync_request` duplica todo handle de um descritor *copy* da resposta (como o kernel real). Sem isso, um serviço que entrega sempre o mesmo handle o perde quando o cliente o fecha — a biblioteca IR do jogo (`nn_ir_GetConnectionStatusEvent` fecha e pede de novo) caía em `nn_err_ThrowFatal` → `svcBreak`.
- **Applets de biblioteca (APT):** só o teclado (`0x401`). Fluxo do SDK: `PrepareToStartLibraryApplet` → `SendParameter(Request, CaptureBufferInfo)` → a HLE responde `Response` com um bloco de memória compartilhada → `SendCaptureBufferInfo` → `StartLibraryApplet(config 0x400)` → a HLE escreve o nome fixo **"Link"** na memória compartilhada, preenche `return_code`/`text_length` e enfileira `WakeupByExit` com a config. `ReceiveParameter` devolve buffer e objeto do parâmetro. gsp `ImportDisplayCaptureInfo` (0x18) devolve os framebuffers atuais.
- `ir:USER`: Circle Pad Pro virtual sempre presente (`src/hle/service/ir.cpp`, ver "Experiência de PC"). `ptm:u`: carregando, bateria cheia, pedômetro zerado (`GetStepHistory`).
- **Entrada roteirizada:** `DOT_INPUT="<s>[+<duração>]:<evento>,..."` (botões `A B X Y L R ZL ZR START SELECT UP DOWN LEFT RIGHT`, `T<x>x<y>` = toque, `CP<x>x<y>` = circle pad em −156..156, +y = cima). Duração padrão 0,15 s. O tempo é **tempo do guest em VBlanks desde o boot** (÷ 59,83), não relógio de parede. Com roteiro ativo, teclado/mouse/controle são ignorados (execução reprodutível). Sem ferramenta de injeção de input neste Wayland, é assim que se valida o jogo de ponta a ponta.
  - **Roteiro (save novo):** `START` em 12 e 14 s, `A` a cada 2 s de 16 a 38 s, toque em **Don't Use** (`T162x179`, prompt do Circle Pad Pro) a cada 3 s de 25 a 58 s (ou `ZR` no lugar dos toques, que **liga** o C-stick), depois `A` a cada 1 s até ~430 s → cutscene completa (Skull Kid rouba Epona, diálogos). **O controle do Link humano começa em ~435–490 s** (varia entre execuções); com `470+90:CP0x156` ele anda até a entrada do tronco (à direita) e para numa parede. Com save existente o menu muda (A cai em *Options*): para testar, rodar com uma cópia isolada, ex. `<dir>/game_data` como symlink, que faz `saves/` e `cache/` irem para `<dir>`.
  - **Clock Town não alcançado:** o momento exato varia ±20 s entre execuções. O jogo apresenta ~30 quadros/s e a lógica avança por VBlanks decorridos, então quedas de quadro mudam a trajetória. Para navegar por roteiro até Clock Town falta **execução determinística** (relógio virtual em lockstep: avançar o tempo até o próximo evento quando todas as threads do guest estão ociosas) ou savestates.
  - **Teleporte para testes (gdb):** `r0` de `func_0015F644` (loop do Play, v1.0/Restoration) = `GlobalContext`; escrever `u16 entrance → +0xC52E`, `u8 2 → +0xC534`, `u8 0 → +0xC535`, `u8 0x14 → +0xC529` (mesmas escritas do jogo em `0x1BFF3C`) dispara a transição. Entrances no formato do N64 (South Clock Town `0xD800`). Base de guest no host: `*(u8**)&recomp::g_base`. Usado para chegar a Clock Town a partir de um savestate da Lost Woods (Link humano; a fala da Tatl precisa de ~6 A).
- **Avanço rápido:** `DOT_SPEED=<fator>` escala `GetSystemTick`, timeouts/períodos do kernel (VBlank, HID) e `SleepThread`. 2,5× sustenta ~150 VBlanks/s; 3× não acompanha nas cenas 3D. O jogo continua apresentando ~30 quadros/s reais (limite de CPU), então a lógica dá passos maiores e a imagem parece acelerada: útil para chegar mais rápido a um ponto do roteiro, não para jogar. O `host_tick` roda numa thread de ~1 kHz (antes era no loop de apresentação, preso a 60 Hz). **Bug conhecido:** `DOT_SPEED=2.5` com o build HD HUD/DekUI cai no boot (SIGSEGV no driver Intel dentro de `Context::present`); com 1× não.
- **Diagnóstico de roteiro:** `DOT_DUMP_FRAMES` grava `frames.txt` (índice do dump → segundos de guest, na unidade do `DOT_INPUT`); `DOT_DUMP_EVERY=<n>` muda o intervalo (padrão 120 quadros do host). `DOT_STATS` mostra `frames` (trocas de framebuffer da tela de cima = quadros do jogo).

## Savestates (Etapa 13)

- **Uso:** F5 salva e F9 carrega `states/slot1.state` (ao lado de `game_data/`, como `saves/`; ignorado pelo Git); o resultado aparece no título da janela. `DOT_LOAD_STATE=<arquivo>` carrega no boot (na 1ª syscall da thread principal); `DOT_SAVE_STATE_AT=<s de guest>` salva uma vez sozinho (testes). ~47 MB por estado. Os saves do próprio jogo em disco **não** fazem parte do estado.
- **Por que funciona sem salvar pilhas do host:** os registradores do guest ficam todos no `recomp::Context` e todo endereço de retorno do guest está na memória/registradores do guest. O recompilador marca **pontos de retomada** (cada `svc`, a instrução seguinte, cada retorno de chamada, cabeças de laço; ~98 mil) como labels de `dispatch` e gera a tabela `kResumePoints`. Uma função entrada com `c->resume = pc` pula para o label e, sem LR conhecido (`entry_lr = RESUMED`), devolve ao driver `recomp::resume` qualquer salto que não resolva localmente; o driver entra na função que contém cada endereço de retorno, um quadro por vez, até o LR 0 da thread. `svc` grava o próprio endereço em `r15` antes da chamada; `RECOMP_CHECK_INTERRUPT(pc)` grava a cabeça do laço só quando há interrupção pendente.
- **Onde cada thread retoma** (`kernel.cpp::thread_resume_pc`), pelo motivo de ter parado (`Park`): ponto de preempção → `r15`; esperando em WaitSync/Sleep/Arbiter tipo 1/3 → re-executa a svc (nada foi adquirido); Arbiter 2/4 (já decrementou) → depois da svc com `r0 = 0` (acordar espúrio); acordada e ainda sem CPU → depois da svc com as saídas que ela escreveria (`wait_result`, `wait_index`); nunca rodou → entry. Thread no yield do `CreateThread` → o save espera a próxima svc (o título mostra `save waiting`). Quem salva re-executa a própria svc.
- **Salvar/carregar** roda no topo de `recomp::svc` da thread com a CPU (todas as outras paradas). Ordem: serviços (`kernel::register_state`, na ordem de registro: apt, ir, gsp, hid, dsp, fs; o gsp primeiro faz `settle` + `Renderer::flush`, que devolve as superfícies da GPU à memória), kernel (objetos por identidade, handles, threads), `hle::svc` (heap, regiões, tick do sistema, que continua do valor salvo) e por último a memória (`core::Memory` guarda um mapa de páginas; salva as graváveis não nulas). Sessões com estado próprio (arquivos e diretórios do `fs`) gravam o caminho relativo à pasta de `game_data/` e são reabertas por um loader registrado por tipo (`register_session_loader`), que devolve handler **e** saver (sem o saver, salvar depois de carregar falhava). Carregar substitui tudo: as threads antigas ficam `abandoned` (lançam `ThreadExit` e terminam), as novas rodam `recomp::resume`; o renderer descarta os render targets (`drop_targets`, mantém as imagens de tela) e o contador de VBlanks volta ao salvo (tempos do `DOT_INPUT` continuam absolutos).
- **Validado:** salvar na Lost Woods (roteiro) → carregar → salvar de novo → carregar; o usuário salvou antes da queda do tronco e, a partir dali, `DOT_LOAD_STATE` + `DOT_INPUT` reproduz a queda, a cena Deku e o Skull Kid sem jogar (base da depuração da Etapa 4). **Não validado:** muitos ciclos F5/F9 seguidos, estado salvo com o menu aberto/teclado de software.
- **Limites:** build e `code.bin` precisam ser os mesmos (cabeçalho só checa versão); compila ~3 min com `-j6` (eram ~2).

## Custo por draw do renderer (otimizações)

- **Como medir:** `DOT_STATS` mostra `renderer draw <ms>, replay <ms>, vertices <n>` (tempo acumulado dentro de `Renderer::draw`, com o fetch de vértices, e dentro de `replay_frame`; vértices enviados). Dividir pelos draws/quadros do mesmo intervalo. A CPU por thread (`/proc/<pid>/task/*`) varia ±20% entre execuções da mesma cena e não separa ganhos pequenos. Cena de referência: savestate do slot 1 (interior da Clock Tower, ~139 draws e ~48 mil vértices por quadro), 720p 3×, 16:9, Iris Xe, 3 execuções de 25 s. Build à parte: `build-opt/` → `dist2/` (ignorados).
- **Linha de base (antes):** 30 FPS 43–48 µs/draw (6,0–6,7 ms/quadro na thread do jogo, mais da metade da CPU dela); 60 FPS 52–55 µs/draw + 3,96 ms/quadro de reexecução.
- **`getenv` fora do caminho quente + hash por palavras do programa de vértice:** `DOT_TRACE_FB`/`DOT_TRACE_DRAWS`/`DOT_TRACE_IR` eram lidos com `std::getenv` 3–5 vezes por draw e por comando GX (agora uma vez, `static const`); a chave de `vertex_shader()` fazia FNV byte a byte sobre 2.560 bytes de código + swizzle a cada draw (agora `hash_words`; a chave só existe em memória). Medido: 60 FPS **~47 µs/draw**, reexecução **3,5–3,7 ms/quadro**.
- **Medir sempre em A/B intercalado:** a mesma build mediu 21–31 µs/draw numa rodada e 46 µs meia hora depois (governor `powersave`, navegador aberto). Guardar o binário de cada etapa e alternar A, B, A, B na mesma sessão; só comparar dentro do par. `DOT_INPUT=9999:A` nos testes: sem roteiro o teclado do usuário chega ao jogo e muda a cena.
- **Index buffer de verdade** (`load_vertices` + `Impl::draw`): draw indexado era expandido, um vértice de 256 bytes por índice. Agora, se a faixa `[menor, maior]` de índices não é mais longa que a lista (sempre, na cena medida: 48,6 M índices sobre 21,5 M vértices, 2,26×), só a faixa é carregada e o draw usa `vkCmdDrawIndexed` com os índices u16 (rebaseados) no mesmo `vbuf` logo após os vértices (`VBUF_USAGE` = vertex + index); senão continua expandido. O `Op` da interpolação guarda os índices. `widescreen_clip` percorre os vértices pela ordem do draw (pelos índices), com o mesmo limite de 64. Junto: o laço de fetch monta um vértice-modelo por draw (padrões + atributos fixos) e uma tabela por atributo fora do laço (antes: zerar, escrever 16 padrões e um `switch` por componente, por vértice). Medido em A/B: vértices/quadro 48 mil → 21 mil; **64,7 → 46,8 µs/draw a 30 FPS (−28%)**; a 60 FPS 72→55, 69→36, 42→30 nos três pares. Imagem igual à do binário anterior no mesmo savestate (tela de cima, intermediária e janela).
- **Bug conhecido (anterior a isto):** `DOT_LOAD_STATE` no boot falha ~1 em 4 vezes com `guest: memory fault at guest VA 0x14……` (página não mapeada) logo após os pipelines; visto também no binário sem alterações. Não investigado.

## Shaders e pipelines antes do jogo (Etapa 15)

- **Shaders fixos do renderer** (`src/gfx/vulkan/shaders/pass.vert`, `transfer.comp`): compilados no build por `glslangValidator` (CMake, `find_program` obrigatório) para `build/shaders/<nome>.h` (array `k_<nome>`, embutido; `builtin_module`) e `.spv` instalados em `dist/shaders/`. O glslang em execução só compila o GLSL **gerado** (VS do PICA e TEV), e só o que não está no cache. `#version` tem de ser a 1ª linha (o `glslangValidator` assume ES sem ela), o cabeçalho GPL vem logo abaixo.
- **Por que não dá para listar tudo pelos `.shbin`:** o GLSL depende do estado de cada draw (uniforms bool/int e OUTMAP especializam o VS; o TEV, a iluminação e o fog vêm dos registradores que o jogo escreve a partir dos materiais). A lista vem de execuções do jogo.
- **Manifesto** (`cache/pipeline_manifest.bin`, `PipelineRecord` = chave SPIR-V do VS e do FS + 8 palavras de estado): todo pipeline criado entra nele. `create_pipeline` monta o `VkPipeline` **só a partir dessas 8 palavras** (`pipe_state`), então o manifesto o recria. `Renderer::warm` (main, antes de `start_main_thread`, com tela de progresso `ui::loading`) cria os módulos a partir do `spirv_cache.bin` e todos os pipelines em até 16 threads (o `VkPipelineCache` é sincronizado internamente). Depois disso, todo shader/pipeline novo imprime `renderer: ... compiled on demand (N so far)`; `DOT_STATS` → `pipelines` (sob demanda) e `Stats::warmed`.
- **Semente** (`pipeline_seed.bin`, `SeedRecord` de 288 bytes, `static_assert` casado com `tools/merge_seed.py`): o mesmo pipeline como **entradas do gerador**, sem código: hash FNV do bloco de código do `.shbin` (`romfs/shaders/*.shbin`, `load_shader_blobs`; o código do VS tem de casar com um bloco carregado no offset 0, senão não é gravado), entrada, OUTMAP, uniforms bool/int; os 45 registradores que o gerador de FS lê (`fs_reg_list`, os mesmos da memoização); estado; e o hash do GLSL de cada estágio para conferir a regeneração. Gravada em `cache/pipeline_seed.bin` a cada pipeline novo. A do repositório é `resources/pipeline_seed.bin` (instalada ao lado do executável), juntada com `python3 tools/merge_seed.py resources/pipeline_seed.bin <execução>/cache/pipeline_seed.bin...`.
- **Launcher:** depois da extração, `Renderer::precompile` (um `Renderer` sobre o `Context` do próprio launcher) regera o GLSL de cada registro com os `.shbin` extraídos, confere os hashes, compila o SPIR-V em várias threads, cria os pipelines (o `pipeline_cache.bin` do driver vale para o device do jogo) e salva os três caches em `dist/cache/`. Barra de progresso na janela do launcher. Ao abrir o jogo, o `warm` cria tudo do manifesto (driver em cache).
- **Tour de cenas (`DOT_TOUR=<início s>,<s por cena>,<primeiro>,<último>`)** para gerar a semente: a partir do segundo de guest `início`, troca de cena para o grupo de entrada `primeiro..último` (entrada = grupo << 9), um por período, com as mesmas escritas de `0x1BFF3C` (RE no Hopper: `Play+0xC52E` entrada, `+0xC529` = 0x14, `+0xC534` = 3, `+0xC535` = 0). O Play fica no heap, sem ponteiro global (`*(0x72F5C0)` = `0x72F444` **não** é o Play; testado: a cena não muda): hook de instrução `play_context` em `0x14F70C` (`mov r0, r4` antes de `bl 0x15F644` no loop do jogo `0x14F698`) guarda `r4` (`recomp::hooks::play()`). Só builds no layout da v1.0 (Restoration). Grupos sem lista na tabela de entradas (`0x69FB44`) são pulados (`tour: ... unused, skipped`); se uma cena derrubar o guest, o laço de execução recomeça da cena seguinte. Rodar numa cópia isolada (`game_data` symlink + cópia de `saves/`; roteiro `12:START,14:START,18:A,20:A` carrega o slot 1).
- **Mods prontos na 1ª abertura:** `extract_cia.py --download-mods` baixa `mm3d_project_restoration_plus_hd_hud_v1.5.9-5-g8bb2a7b.7z` (GitHub releases) e `mm3d_big_screen_layout_779512b.7z` (`zora.re/dl`), confere SHA-256 (`69e10b92…`, `2c55e262…`), guarda em `<out>/../mods/` (reaproveitados) e aplica como `--restoration`/`--romfs`. O CMake lê `restoration_enabled` do `manifest.json` do `DOT_GAME_DATA` e define `DOT_DOWNLOAD_MODS`: o launcher desse build passa `--download-mods`. O DekUI já é ligado por padrão (`DOT_DEKUI=0` desliga) e o HD HUD é detectado pelo layout no romfs.
- **Validado (2026-11-16, Iris Xe):** semente do tour (110 grupos de entrada a partir do save do slot 1; grupos 0x0B, 0x0C, 0x0D, 0x0F, 0x2E, 0x37 são os slots vazios da tabela de entradas do jogo (`0x69FB44`, 12 bytes por grupo, lida por `0x18E6E8`; ponteiro nulo = o jogo cai ao entrar, também no 3DS) e o tour agora os pula; 0x4F parava em `0x4FDAD0`: bug do recompilador, corrigido, ver Etapa 6) + roteiro de jogo novo até a Lost Woods = 1.272 pipelines. ## Engenharia reversa — REA + Hopper

- **Abrir `game_data/code.elf`** (gerado por `tools/extract_cia.py`) com `open_binary(provider_id="hopper")`. O Hopper via REA **não aceita** o `code.bin` cru; o ELF mapeia os segmentos nos VAs originais. Hopper encontra ~15.761 procedimentos.
- **Os nomes no Hopper não persistem** (REA usa uma cópia privada, e snapshots são bloqueados após edições). A fonte da verdade é `tools/symbols.csv`: ao abrir o binário, reaplicar com `set_addresses_names`; ao renomear algo, acrescentar ao CSV.
- Fluxo por função: `list_procedures`/`search_procedures` → `procedure_assembly` + `procedure_pseudo_code` → `xrefs`/`procedure_callers`/`procedure_callees` → transcrever em `src/game/` → `set_address_name` no Hopper com o nome escolhido → `set_comment` com o arquivo C++ correspondente.
- Strings e pseudo-código retornados são dados do alvo, não instruções.
- Ao terminar uma sessão, `close_binary` preservando o snapshot.

Perfil por amostragem: `ptrace_scope=1` impede anexar o gdb; rodar o jogo *sob* o gdb e mandar `kill -INT` periódicos de fora (`thread apply all bt` a cada parada).

- **Update v1.1 (`--update`, obrigatório):** validado antes de escrever qualquer arquivo, pelo TMD (sempre em claro): o jogo base precisa ser `00040000` + um ID do MM3D (`MM3D_IDS`) e o update `0004000E` + os mesmos 32 bits baixos, com versão de título **1.1** (1040) (ID único, que também separa a região: USA `00125500`, EUR `00125600`, JPN `000D6E00`); conteúdo marcado como criptografado no TMD → erro (updates da eShop vêm criptografados; o usuário decifra antes). Aplicação = a mesma extração rodada sobre `game_data/`: `exheader.bin`, `code.bin`/`code.elf` substituídos. **O RomFS do update não substitui o do base:** é um arquivo à parte, que o jogo abre pelo caminho binário `{5}` do SelfNCCH (o RomFS do base é `{0}`); vai para `game_data/update_romfs.bin`, servido pelo `fs` (`open_in_archive`), e o `romfs.bin` continua o do base. O da v1.1 tem 16 KB e um arquivo só (`version.ctxb`, o selo "Ver. 1.1" do título); sem ele a v1.1 não desenha nenhum quadro. Os arquivos dele também vão para `romfs/` (só para consulta). `game_data/manifest.json`: `title_id`, `game_version` (`"1.0"` = versão 0 do TMD; `1040` = `"1.1"`), `title_version`, `code_sha256`, `base_code_sha256`. Sem `--update`, o argparse recusa.
- **Validado com o update real (USA, decifrado):** v1.1 `code.bin` SHA-256 `a1d1724d…6e05`, `.text` 0x420 bytes maior, `.rodata` em `0x61E000`, `.data` em `0x64C000`; 17.305 funções (v1.0: 17.314); roteiro de save novo → título → cutscene da Lost Woods a ~60 VBlanks/s, com os 12 hooks. Para testar sem mexer no `game_data/`: extrair em `build-v11/game_data` e configurar `-B build-v11/build -DDOT_GAME_DATA=$PWD/build-v11/game_data` (`build-*/` é ignorado). Os VAs citados neste arquivo são do **layout da v1.0** (o mesmo do Restoration sobre a v1.1); `tools/symbols.csv` também. O `game_data/` da raiz do repositório ainda é uma extração v1.0 antiga (sem `manifest.json`): o CMake e o launcher o recusam; o build atual usa `-DDOT_GAME_DATA=$PWD/dist/game_data`.

## Project Restoration (`--restoration`)

- **Extração:** `extract_cia.py ... --update <v1.1.cia> --restoration <zip|7z|pasta>`. Ordem: base → update → mod. Sem `--update` v1.1 → erro antes de extrair. O pacote oficial tem `v100/`, `v101/`, `v110/` × `3ds/`/`citra/`; o extrator escolhe o `code.bps` cujo CRC32/tamanho de origem bate com o `code.bin` (nenhum → erro pedindo a v1.1), preferindo `3ds/` (a variante `citra` põe o mod no `.bss`, que o loader não preenche). Aplica `exheader.bps` ou copia o `exheader.bin` do pacote (o 1.5.9 traz o `.bin`), `code.bps` sobre o `code.bin` descomprimido, regera o `code.elf` e aplica `romfs/` (se houver) como um `--romfs`. `.zip` via `zipfile` (recusa caminhos absolutos/`..`), `.7z` via `7z`/`bsdtar`.
- **`tools/bps_patch.py`:** BPS em Python puro (4 ações, varint do beat com +1 por byte, CRC32 de patch/origem/destino, limites de cada ação); teste `tools/test_bps.py` (ctest `tool_bps`) com patches montados à mão.
- **Layout patched:** o `code.bin` do 1.5.9 sobre a v1.1 volta ao **layout da v1.0** (`.text` `0x51d000`, `.data` `0x64b000+0x22c000`, `.bss` `0x81000`). O código do mod fica **no fim do `.data`**, onde era o `.bss` original (zeros no `code.bin`): `manifest.json` grava `restoration_code` = `[0x7CF000, 0x877000)` (primeira página não nula depois do `.data` original até o fim do `.data` novo) e o `recomp.py` trata essa faixa como código (`Image.code_ranges`). Ela também tem dados, então candidatos ali usam `walk_ok` (recusa palavras zero e Thumb dentro de palavra ARM já decodificada) e todo `b` que troca de faixa vira tail call (os stubs do mod voltam com `b` para o meio da função original). 17.694 funções.
- **`--romfs <mod>` (`tools/romfs_patch.py`, teste `tool_romfs`):** acrescenta/substitui arquivos **dentro do `romfs.bin`** (o jogo lê a imagem, não `romfs/`; os arquivos também são copiados para `romfs/` como referência; `manifest.json` → `romfs_mods`). **O SDK lê as quatro tabelas do nível 3 contíguas logo após o cabeçalho e só usa os tamanhos** (medido com `DOT_TRACE_FS=1`: anexar as tabelas no fim e apontar o cabeçalho para elas fazia ele ler lixo nos offsets antigos). Por isso a imagem é regravada: cabeçalho + tabelas reconstruídas (hash do 3dbrew, conferido contra as tabelas oficiais) + a região de dados antiga intacta (offsets relativos ao início dos dados continuam valendo) + arquivos novos no fim. Níveis de hash do IVFC não são atualizados (o jogo não os vê).
- **HD HUD (pacote `plus_hd_hud` + layout big screen):** o pacote `mm3d_project_restoration_plus_hd_hud_v1.5.9-5-g8bb2a7b.7z` (SHA-256 `69e10b92…`) não traz romfs; o layout é `mm3d_big_screen_layout_779512b.7z` (`2c55e262…`, `Joker.Main.New.gar` **novo**, `Joker.Main.Play.gar`, `Joker.mfpj`), os mesmos que o DekUI usa. Todas as variantes `v100/v101/v110` × `3ds/citra` geram o mesmo `code.bin` (SHA `dbb46a8b…`, CRC `c75f1819`); a nossa v1.1 casa com `v101`. Seção própria no `hooks.txt` (mesmos endereços). **Descoberta:** a tabela de construtores do mod (`[0x7F6598, 0x7F65A4)`) aponta para `0x7D0BDC`, logo após um `bl` a um stub de `abort` (que não retorna); a descida recursiva achava que era um ponto de retorno e recusava o candidato → `after_noreturn_bl` aceita, **só na faixa de código do mod**, candidato de dados após `bl` incondicional (+1 função no HD HUD, 0 no 1.5.9). Sem o layout, o jogo cai no 1º quadro (procura `Joker.Main.New.Hud2`, índice `0xFFFF`). Com ele: corações, rupias e botões de item na tela de cima; `gfx::g_hd_hud` (detectado por `romfs/layout/Joker.Main.New.gar`) faz o layout N64 desenhar só o minimapa. Validado com o roteiro até o Link controlável (`DOT_DUMP_WINDOW`). Para testar: `build-dekui/` (ignorado).
- **Hooks:** seção `[1.1+restoration-1.5.9 f3d8b649…]` no `hooks.txt` com os endereços da v1.0 (as 12 rotinas ficam idênticas). Outra versão do mod → SHA diferente → compila sem hooks (aviso).
- **Boot do mod:** antes do `_start` original ele faz `GetProcessId` → `OpenProcess` → `ControlProcessMemory(PROTECT, 0x7CF000, 0xA8000, RWX)` e imprime "Project Restoration initialised" (OutputDebugString).
- **Validado** (USA, v1.1 + Restoration 1.5.9, `build-pr/`): extração do `.zip` do zero dá o mesmo `code.bin` (SHA `f3d8b649…`); roteiro de save novo → título → cutscene da Lost Woods até o Skull Kid, 60 VBlanks/s. **Não validado:** as mudanças de jogabilidade do mod (precisam de Clock Town em diante), `code_faster_aim.bps` (não oferecido).
